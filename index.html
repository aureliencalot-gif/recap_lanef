Stratégie de migration Core Banking System

👤 Owner : Aurélien Calot (Theodo Fintech) 📅 Mise à jour : 22/05/2026 — v8 🔒 Usage interne — Confidentiel
Contexte
La Nef est une coopérative bancaire agréée ACPR dont le Core Banking System actuel (Capital Banking Solutions / CBS) génère des dysfonctionnements majeurs : reportings réglementaires erronés, blocages sur les nouveaux produits crédit et épargne, instabilité des API, difficultés comptables, manque d'ouverture pour NefLab. L'éditeur CBS exige par ailleurs une montée de version lourde (modules crédit + comptabilité).

Deux jalons produit structurent le calendrier : la carte pro (en production depuis 2026 avec risques qualité API CBS) et le compte courant particulier + carte (go-live cible : Q4 2027). Les équipes internes sont volontairement réduites — modèle d'externalisation forte, périmètre tout-en-un impératif (solution + hébergement + infogérance + TMA).

Mail La Nef 21/05/2026 : La Nef demande formellement trois scénarios dans la réponse au RFP : (1) Big Bang global, (2) Migration progressive, (3) Build-forward Lot 1 — compte courant particulier + carte mis en œuvre directement dans le nouveau CBS pour Q4 2027, sans développement préalable dans CBS actuel. Le questionnaire joint précise les attendus : modules, interfaces, comptabilité, lotissement des lots suivants.
Critères de sélection
#CritèrePourquoi ?
1Maîtrise du risque réglementaire & comptableLa Nef est sous agrément ACPR avec des reportings déjà erronés. Toute cohabitation entre deux CBS crée un risque de double comptabilité pouvant menacer l'agrément.
2Capacité opérationnelle de la NefLes équipes internes sont très réduites. Faire cohabiter deux CBS, deux éditeurs, deux infogérances mobilise une capacité de pilotage que la Nef ne dispose pas.
3Time-to-market sur les jalons critiquesLe compte courant particulier + carte est attendu pour Q4 2027. La stratégie ne doit ni bloquer ce jalon ni forcer deux chantiers CBS en parallèle.
4Coût total de la transitionUn double run (deux CBS, deux hébergements, deux TMA) génère des coûts cumulatifs pouvant annuler l'avantage du progressif sur le Big Bang.
5Réversibilité & risque d'échec projetUn échec de migration sur un établissement de crédit agréé a des conséquences réglementaires graves. La stratégie doit intégrer des points de contrôle et des options de rollback.

Analyse détaillée — Scénario 3 (Build-forward Lot 1)

✓ Avantages

  • Tient le jalon Q4 2027 sans dépendre d'une migration complète du SI
  • Périmètre isolé (compte part + carte) : faible interdépendance avec crédit, épargne pro, parts sociales
  • ~15 000 clients part = volumes faibles → premier live Mambu à risque maîtrisé
  • NefLab se branche nativement sur les APIs Mambu dès Lot 1 — c'est l'objectif originel
  • Chaque lot suivant bénéficie du retour d'expérience et de l'outillage de migration déjà rodé
  • Rollback du Lot 1 possible sans toucher au reste du SI
  • Processeur carte géré end-to-end par Mambu (avec Marqeta)

✗ Risques & inconvénients

  • Double comptabilité partielle : compta client dans Mambu, compta générale dans CBS → imports comptables non temps-réel, risque d'écarts
  • Vision 360 fragmentée : le gestionnaire navigue entre CBS (crédit/épargne pro) et Mambu (compte part) → Forest A1 obligatoire dès Lot 1, coût supplémentaire
  • CBS sans interfaces standards pour recevoir des données d'un CBS tiers → développements spécifiques CBS à chiffrer et négocier (point de contention)
  • Mambu sans évolutions réglementaires FR hors paiement en run → TMA Theodo dédiée à provisionner sur toute la durée du dual run
  • Double hébergement + double TMA = surcoût récurrent pendant toute la période progressive
  • Risque de "progressif sans fin" si les lots 2-5 glissent : deux CBS actifs sur 4-5 ans
  • Parts sociales hors scope Mambu : traitement à reporter, à contractualiser séparément

⚠ Points de vigilance

  • La compta générale reste CBS jusqu'au dernier lot — le "vrai Big Bang" comptable est différé, pas évité
  • Le plan de lotissement Lots 2→5 doit être défini dans la réponse au RFP, pas en cours de projet
  • La question comptabilité générale + reporting réglementaire est le point le plus sensible pour l'ACPR — réponse très précise attendue dans le questionnaire La Nef
  • Aligner avec Oaklen sur le processeur carte avant la soumission
  • Demander à CBS la documentation de ses interfaces d'import (vision 360, compta) dès le cadrage — c'est le point de faisabilité non confirmé
Recommandation
Scénario recommandé : 3. Build-forward Lot 1 Recommandé — avec Scénario 1 (Big Bang) comme ambition finale Si planning tient

Parmi les trois scénarios demandés, le Scénario 3 (Build-forward Lot 1) est le plus adapté à la situation actuelle de La Nef : il est le seul qui garantit le jalon Q4 2027 sans dépendre d'une migration complète, tout en posant les fondations de la migration globale. La Nef l'a elle-même formalisé comme livrable obligatoire, ce qui signifie qu'elle est prête à assumer le dual run — à condition que le lotissement soit clair et la comptabilité sous contrôle.

La stratégie narrative dans la réponse au RFP : on répond aux trois scénarios demandés, on chiffre chacun honnêtement, et on recommande le Scénario 3 comme point d'entrée avec le Scénario 1 comme cible dès que le planning le permet. Le Scénario 2 (progressif global) est la voie intermédiaire si le Big Bang s'avère trop risqué mais que la Nef veut avancer sur l'ensemble du périmètre plus vite que le Scénario 3 lot par lot.

Condition non négociable dans la réponse : être très précis sur la comptabilité — compta client dans Mambu, compta générale dans CBS pendant le dual run, TMA Theodo pour les évolutions réglementaires hors paiement, chiffrée explicitement. C'est ce que l'ACPR regardera et ce que le questionnaire La Nef demande explicitement.

Annexes

A. Périmètre CBS actuel (Capital Banking Solutions)

  • Tenue de compte (particuliers et professionnels)
  • Crédit (particuliers et professionnels) — module concerné par la montée de version exigée par CBS
  • Comptabilité bancaire — source des reportings réglementaires ; concernée par la montée de version
  • Reporting réglementaire (via éditeur tiers racheté par CBS)
  • ~18 applications périphériques connectées (WeBank/Alsimaray, NefLab, KYC/AML, virements BPCE PS, etc.)

C. Contraintes communes aux scénarios 2 & 3 (approche progressive)

  • CBS ne dispose pas d'interfaces standards pour recevoir des données d'un CBS tiers : développements spécifiques nécessaires côté CBS
  • La vision 360 client, la gestion des limites/autorisations et le calcul des prélèvements sont profondément imbriqués dans CBS
  • Mambu ne gère pas les évolutions réglementaires françaises hors paiement en run — TMA Theodo dédiée à provisionner explicitement
  • Forest Admin (C1) sert de couche de réconciliation bi-CBS mais ajoute un coût de licence et une dépendance supplémentaire

D. Recommandation de l'auditeur CBS externe

L'auditeur financier mandaté par la Nef a conclu : (1) migrer la comptabilité en premier, (2) un Big Bang est nécessaire car la Nef ne peut pas réussir une migration seule, (3) la montée de version CBS est l'alternative si la migration s'avère infaisable. Ces conclusions renforcent le Scénario 1 comme cible finale et soulignent le risque de laisser traîner les scénarios progressifs sur plusieurs années.
